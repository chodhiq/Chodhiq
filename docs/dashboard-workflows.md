# Admin dashboard workflows and guard impact

## One-page summary

**Audit basis:** live source under `admin-dashboard/app` and `admin-dashboard/lib`, shared `supabase/migrations`, and the current guard migration. Archived build and ZIP copies were excluded. Statuses mean code and migration evidence only; no live authenticated end-to-end test was run.

- **Workflows inventoried:** 30
- **WORKS:** 19
- **LOOKS BROKEN:** 7
- **AFFECTED by the new guards:** 2

Five highest-priority problems:

1. Provider detail edits directly write `sponsored_rank` (protected) and even ordinary editable fields use authenticated client writes; non-admin DB identities fail the provider trigger. The UI reports “The action could not be completed. Refresh and retry.” (`admin-dashboard/app/providers/[id]/page.tsx:184`; generic message in `admin-dashboard/lib/admin.tsx:153`).
2. Bulk provider suspension directly writes `verification_status` and `is_verified`, both protected. Same generic error (`admin-dashboard/app/components/enhanced-list-pages.tsx:64`).
3. Review business application calls `review_business_application`, but its definition exists only in dashboard-local `admin-dashboard/db/admin_routed_operations.sql` (not shared `supabase/migrations`); shared production migrations instead define business verification schema separately. If that local SQL was not independently applied, every decision fails with the generic mutation message (`admin-dashboard/app/applications/page.tsx:125`).
4. Community post/comment moderation and report resolution RPCs are absent from shared migrations; definitions occur in dashboard-local staging SQL only. Deployments applying only shared migrations return PostgREST “function not found”; UI shows generic mutation failure (`admin-dashboard/app/components/report-queue.tsx:114`, `:195`; comment `admin-dashboard/app/components/community-comments.tsx:78`).
5. Campaign performance/enquiry sources include `ad_campaign_performance` and campaign insertion includes `approved_by`, `approved_at`; shared schema defines `ad_campaign_events` and `ad_campaign_invoices` but not `ad_campaign_performance`. The combined load fails wholesale (“Advertising records could not be loaded.”); campaign status changes can also fail if those columns are absent (`admin-dashboard/app/campaigns/page.tsx:104`, `:257`).

## 1. Overview

- **Framework:** React 19 app-router code authored for Next.js-compatible `vinext`; Vite and Cloudflare plugin build it. Hosting entry is a Cloudflare Worker (`admin-dashboard/worker/index.ts`), configured in `admin-dashboard/vite.config.ts`. Application source is in `admin-dashboard/`; routes live in `admin-dashboard/app/`, shared auth and operations in `admin-dashboard/lib/`.
- **Supabase key:** browser client uses the public anon/publishable key, with a persistent user session; no service-role key is used by the dashboard client. Variables: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY`, read in `admin-dashboard/lib/supabase.ts:3-4`, documented in `admin-dashboard/README.md:17-22`. Trusted Edge Functions receive `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` through managed secrets (names only; `admin-dashboard/README.md:22`).
- **Sign-in / admin check:** `signInWithPassword` in `admin-dashboard/app/components/admin-shell.tsx:682`; `AdminProvider` restores the session and subscribes to auth changes in `admin-dashboard/lib/admin.tsx:68-109`. Browser gate requires `session.user.app_metadata.role === 'admin'` (`admin-dashboard/lib/admin.tsx:208-214`; shell gate `admin-dashboard/app/components/admin-shell.tsx:378-413`). Permission navigation uses a local admin-level matrix (`admin-dashboard/lib/permissions.ts:1-20`) based on `app_metadata.admin_level`. Database authorization is authoritative through `public.is_admin()` and `public.admin_has_permission(text)` in `supabase/migrations/20261023110000_admin_permission_enforcement.sql:4,22`; migration restrictive RLS policies bind tables to named permissions. The browser does not call those functions directly on every action; RLS and the SECURITY DEFINER RPCs enforce them. Guard trigger on verification explicitly calls both functions (`supabase/migrations/20261106100000_protect_verification_and_provider_fields.sql:24`).
- **Routes:** `/` dashboard; `/applications`; `/providers`; `/providers/[id]`; `/verification`; `/activity`; `/demand`; `/users`; `/categories`; `/reviews`; `/community`; `/community/privileges`; `/moderation/community`; `/moderation/providers`; `/reports/community`; `/reports/providers`; `/campaigns`; `/notifications`; `/analytics`; `/payments`; `/subscriptions`; `/admins`; `/audit`. Payments/subscriptions nav entries are hidden unless `NEXT_PUBLIC_ENABLE_MONETISATION` is true (`admin-dashboard/app/components/admin-shell.tsx:25-29,70-76`). Reports aliases render the moderation queues. Route source inventory is the page files under `admin-dashboard/app/`.

### Permission-model caveat

The shared permission migration gives moderator/support `applications.review`, moderator `providers.suspend`, etc., but the new verification trigger permits direct client field edits only when the caller is `is_admin()` **and** `admin_has_permission('applications.review')`. User-facing `isAdmin` is a JWT app-metadata check, while DB `is_admin()` and `admin_has_permission()` resolve the trusted admin registry. The provider trigger lets any DB administrator bypass provider protected columns irrespective of the specific permission; non-admin logged-in identities are blocked.

## 4. Likely breakage, ordered by impact

1. **Provider detail edit and suspension (AFFECTED).** Exact UI error: “The action could not be completed. Refresh and retry.” Detail edit sends `sponsored_rank` (`admin-dashboard/app/providers/[id]/page.tsx:177`); suspension sends `verification_status,is_verified` (`:231-234`). Bulk suspend sends `verification_status,is_verified` (`admin-dashboard/app/components/enhanced-list-pages.tsx:64`). Before the guard, the direct update could work for a DB identity whose RLS permitted admin writes; dashboard `admin.act` still checked the admin JWT role. Smallest robust fix: route trust/status fields through an authorization-checked SECURITY DEFINER RPC; if detail should only edit business details, remove `sponsored_rank` from this update or include it in the RPC. A mere permission change will not bypass the provider trigger for a DB role that is not `is_admin()`.
2. **Business application decisions (LOOKS BROKEN).** Exact UI error: “The action could not be completed. Refresh and retry.” The referenced `review_business_application` is absent from shared migration history; only local staging SQL defines it (`admin-dashboard/app/applications/page.tsx:125`). Before guard: same missing RPC means it would fail unless separately deployed from local staging SQL. Smallest fix: add/apply the intended transactional RPC in shared migrations (or change UI to an existing authorized RPC, if semantics fit).
3. **Community post and comment moderation (LOOKS BROKEN).** Exact UI error: generic mutation message. RPCs `admin_transition_community_post` and `admin_transition_community_comment` called at `admin-dashboard/app/components/phase2-pages.tsx:176`, `admin-dashboard/app/components/report-queue.tsx:195`, `admin-dashboard/app/components/community-comments.tsx:78` have definitions only in dashboard-local SQL, not shared migrations. Before guard: same issue unless deployed separately. Smallest fix: add/apply the RPC definitions via shared migration.
4. **Report resolution (LOOKS BROKEN).** Exact UI error: generic mutation message. `admin_resolve_report` called at `admin-dashboard/app/components/report-queue.tsx:114,163`; definition appears in dashboard-local staging SQL, not shared migration files. Before guard: same issue unless independently applied. Smallest fix: move the reviewed transactional RPC into shared migration history and deploy it.
5. **Campaign list and transition (LOOKS BROKEN).** Exact list error: “Advertising records could not be loaded.” The page queries `ad_campaign_performance` at `admin-dashboard/app/campaigns/page.tsx:104`; shared schema defines campaign events, not this table/view. Approve/pause writes `status,updated_at`, with approval `approved_by,approved_at` at `:257-263`; confirm those columns and authenticated grants exist in the target schema. Before guard: the absent relation already makes the whole campaign page report failure; status writes could work only if schema and RLS permit. Smallest fix: query an existing performance source or add the missing view, then confirm/write only existing columns through permission-checked path.
6. **Campaign creation storage path (UNCHECKED).** UI error: “Campaign could not be created. Check the image and try again.” `ad-creatives` bucket policies are deployment setup, not present in shared schema evidence inspected. Before guard: still fails if bucket/policies absent. Smallest fix: provision the bucket and scoped policy through reviewed deployment migration.
7. **Verification visibility itself (UNVERIFIED potential operational issue, not counted in the totals).** If an admin lacks `applications.review`, the trigger still lets that identity read requests, but mutations via RPC correctly fail with DB authorization; dashboard wrapper text is generic. This guard effect is intentional and does not classify the RPC workflow as AFFECTED because it uses SECURITY DEFINER. Grant the intended permission or surface the permission-specific RPC error if operator clarity is desired.
