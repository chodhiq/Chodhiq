# Profile-tab crash investigation

## Result

No cause is confirmed. The current Profile tab and all three requested fixture variants render without a crash in the test harness. The real Android crash is not reproduced by this Jest test.

The requested command, `npx jest __tests__/repro/profile-tab-crash.test.tsx`, reports `No tests found, exiting with code 0`: `package.json` limits `testMatch` to `__tests__/buttons/**/*.test.ts?(x)`. Running the same test with a CLI `testMatch`/`roots` override executes it:


The single test switches to the Profile tab, advances 2.1 seconds, checks the local and app-level fallback text and uncaught console errors, and repeats against: the reported account shape, a booking with its provider relation missing, invalid account/booking/notification dates, and an unrecognized notification type. A Worklets native-version warning comes from the existing Jest mock; it is not a test failure.

The test uses the real `RootNavigator`, its tab bar, Profile screen and screen boundary, with the shared `buttons/helpers.tsx` state fixture. The helper mocks `useAppState`, so this verifies rendering of the final context values, not the real `AppStateProvider`’s startup/network/push side effects. Jest also runs on Node, not the Android JS engine.

## 1. Why the Profile boundary can miss an error

In `src/navigation/RootNavigator.js:60-65, 92-109`, `Profile` is registered with `ProfileTabScreen`. That component wraps `AnimatedProfileScreen`—the `withScreenMotion(ProfileScreen, 'subtle')` HOC and everything it renders—in `ProfileScreenErrorBoundary`. Therefore the boundary includes the screen, its `ScreenSurface`, profile card, menu cards, buttons, and bottom sheet subtree.

It does **not** wrap the `Tab.Navigator`’s custom `GlassTabBar` (`RootNavigator.js:92-94`), its `TabItem`s, navigator option/descriptor calculation, the parent `RootNavigator`, or `AppStateProvider`/theme ancestors. `headerShown: false` means there is no Profile header in this tab configuration; the tab bar is a sibling, not a child of the Profile route boundary. The local boundary’s render/`componentDidCatch` behavior is in `src/components/ProfileScreenErrorBoundary.js:8-42`.

Places outside that boundary which can throw during a Profile activation or resulting state update:

### Which errors produce that exact fallback?

That text is rendered when the `Sentry.ErrorBoundary` in `App.js` captures an error in its React subtree and enters its fallback state. This includes synchronous errors during render, constructors, and React-managed commit/lifecycle work (including a synchronous exception thrown by a descendant effect if React routes it to the nearest boundary). If the error is under `ProfileScreenErrorBoundary`, the Profile fallback should win instead; errors in its siblings/ancestors can reach the App fallback.

An exception thrown later by a timer callback or an event handler is not caught by a React error boundary. A rejected promise / async continuation is likewise not automatically caught. Those can reach React Native’s global exception handler, be logged/reported by Sentry, or be caught by application code, but do not by themselves render this exact App fallback. A state update performed after an async operation can, however, cause a **new synchronous render** to throw; that render error can produce the fallback. `safePress` catches button-action errors and reports/toasts them (`src/lib/safePress.js:17-52`); profile avatar/logout handlers also catch their own awaited errors (`ProfileScreen.js:81-118`). AppState startup and notification errors are generally caught/logged by their async callers, not converted to this fallback.

## 5. Ranked hypotheses and smallest proposal

1. **A `GlassTabBar` render/commit/animation-adjacent error is outside the Profile route boundary.** Evidence: tab focus immediately changes its focused index and activates shared-value effects; it is a sibling supplied by `tabBar`, so its React errors go to the app boundary. The requested delay is compatible with a commit/update after focus. Against: the active indicator/label changes are ordinary operations; Jest’s Reanimated mock passed and cannot validate the Android native/worklet path. **Smallest proposal:** add a dedicated error boundary around the custom tab-bar element to keep a tab-chrome render failure from replacing the whole app; use a device stack before changing the animation itself.

2. **An account-load state update causes a parent/provider render error outside the Profile boundary.** Evidence: `AppStateContext` performs asynchronous account/profile/saved/booking/notification updates while a signed-in user can already navigate; provider value computation is above RootNavigator. Against: the supplied name, single review/reply, cancelled booking, empty saved list, and one notification all map to safe shapes; the final-value navigator test passes. The provider’s real async path was not exercised by this test. **Smallest proposal:** if a device stack points to provider value creation, normalize/guard `profile` once before building the value and validate the offending account row at its mapper boundary.

3. **A device-specific date/`Intl` or image-source value fails during account mapping or a later render.** Evidence: account mappers now use `Intl.DateTimeFormat`; Android ICU/JS-engine behavior and unexpected avatar URI types are not covered by Node/Jest. Against: invalid date inputs return empty strings in shared helpers, the fixture’s avatar is null, notification type handling is generic, and this test passes all three requested edge cases. A synchronous `mapProfile` error during the startup promise would normally hit the startup catch/log rather than render the global fallback; it would need to escape in a React render/commit path to produce the exact screen. **Smallest proposal:** capture the device stack and inspect actual mapper inputs first; then add targeted validation/fallback only for the confirmed unsupported value/runtime.
