# Android walkthrough issue report — 11 October 2026

## Scope and confidence

Reviewed the full 4:01 portrait screen recording (`video_2026-10-11_17-14-18.mp4`) at three-second intervals and traced the visible customer-app behavior through the current workspace source and release notes. Times below are approximate offsets within the clip. The recording does not show an app version or device/Android version, and the current workspace has pre-existing uncommitted changes. Findings therefore distinguish what the recording proves from what still needs a build or backend check.

## Findings

| ID | Priority | Finding | Assessment |
| --- | --- | --- | --- |
| CQW-01 | P1 | WhatsApp quote link rejects the provider number | **Confirmed failure in the recording and current code path.** Around 01:45–02:00, WhatsApp reports that it cannot find the number because the country code is missing or incorrect. The quote handler removes punctuation and sends the remaining digits directly to `wa.me`; a UK local number beginning with `0` remains in local form. The app has already saved the quote request before opening WhatsApp, so the ChodhiQ lead may be recorded while the actual WhatsApp message is not delivered. See [`ProviderDetailScreen.js`](../src/screens/ProviderDetailScreen.js#L164) and its `wa.me` construction at line 187. |
| CQW-02 | P2 | Map has a basemap but no business locations | **Confirmed symptom; backend cause unverified.** Around 02:35–02:55, map tiles render, but the app says “Map locations unavailable” while Search has businesses. Search for coordinates calls the `public_provider_coordinates` RPC; providers without valid returned coordinates are excluded from the map. The migration defining that RPC is present locally, but the recording cannot establish whether it was deployed, callable by the installed build, or returned coordinates for these listings. Inspect the deployed RPC result and its error/logs, then check which published providers have a non-null `base_location`. See [`providerRepository.js`](../src/data/providerRepository.js#L108) and [`DiscoveryScreens.js`](../src/screens/DiscoveryScreens.js#L153), [empty-state UI](../src/screens/DiscoveryScreens.js#L488), and [`public_provider_coordinates` migration](../supabase/migrations/20260928120000_public_provider_coordinates.sql#L1). |
| CQW-03 | P2 | Google sign-in fails on the recorded Android build | **Failure is visible; configuration mismatch is the likely cause.** Near 03:45, the sign-in page shows an Android Google OAuth configuration error referring to the app package and signing certificate. The source maps Google `DEVELOPER_ERROR` / status 10 to this message. The native sign-in path also requires a web client ID, while beta/release config validates the web client ID and Android signing SHA-1. Compare the installed APK’s package and signing certificate with the Android OAuth client registered for this app, and confirm the client ID embedded in that exact build. Email/password and guest options remain visible in the recording. See [`authOperations.js`](../src/lib/authOperations.js#L30), [`googleSignIn.native.js`](../src/lib/googleSignIn.native.js#L8), and [`app.config.js`](../app.config.js#L111). |
| CQW-04 | P2 | The shown provider profile is substantially incomplete | **Confirmed content gap in this listing.** The DRD profile shows no description, services, active offers, or verified business photos. These screens use explicit empty states driven by provider data; this is not evidence of a layout or loading defect. Check the listing with its owner and verify its current details and publication status before using it as a representative customer-facing profile. See [`ProviderDetailScreen.js`](../src/screens/ProviderDetailScreen.js#L308) and [`ProviderDetailComponents.js`](../src/components/ProviderDetailComponents.js#L226). |
| CQW-05 | P2 | Notification preference sync keeps returning to a retry state | **Repeated retry/sync state observed; underlying failure is not identified.** The profile shows “Retrying…” / notification sync feedback in separate parts of the recording. The app retries registration on startup and whenever Android returns to the foreground. Its error handler distinguishes missing FCM configuration, denied permission, missing account profile, timeout, and other failures, but the recording does not show enough of the final error to select one. Capture the exact settled error on the same installed build and check Android notification permission, Firebase/FCM configuration, and the matching profile row. Recent readiness notes also say push and vibration still require signed-device verification. See [`useCommunicationPreferences.js`](../src/hooks/useCommunicationPreferences.js#L44), [`pushNotifications.js`](../src/lib/pushNotifications.js#L16), [`pushRegistrationErrors.js`](../src/lib/pushRegistrationErrors.js#L1), and [beta readiness](BETA_LAUNCH_READINESS_2026-10-07.md#L30). |
| CQW-06 | P3 | Locality shown in Search may not match the Birmingham context | **Potential expectation mismatch, not a confirmed filtering bug.** The app header initially says Birmingham while the visible DRD listing shows a London locality. Search intentionally defaults to “Any city” and “Any area”; the “In my area” filter is opt-in. Thus a London result is allowed by the current implementation, though it may surprise someone arriving from a Birmingham discovery screen. Consider making the active area/filter state clearer or defaulting this entry path to the selected city if local-only results are intended. See [`ExploreScreen.js`](../src/screens/ExploreScreen.js#L41) and the area filter at line 537. |

## Other visible states

- “No quote requests yet” is consistent with an empty account and is not a failure by itself.
- “All caught up” on Notifications is a normal empty state.
- The repeated “Delete review?” prompt is a confirmation screen. The clip does not establish that deletion was confirmed or failed.
- Android launcher, account chooser, and WhatsApp screens are external system/app surfaces. Their appearance is expected; the invalid WhatsApp destination itself is CQW-01.

## Recommended order

1. Fix and verify UK phone-number normalization for the WhatsApp link, including already international numbers, and ensure the UI does not imply that a WhatsApp message was delivered merely because the link opened.
2. Check the deployed provider-coordinate RPC and live coordinate coverage; re-open Map on the same build after correcting the backend or data issue.
3. Verify the Android OAuth client against the exact APK package name and signing SHA-1, then retest Google sign-in on that APK.
4. Resolve the notification registration error on a signed Android build and verify permission, token registration, and the vibration preference.
5. Complete and owner-check the displayed provider profile; clarify the Search area context if cross-city results are not intended.

## Limits

This was a recording and source investigation, not a live backend session or replay on the device. The installed build identity is unknown. The workspace readiness record says beta v28 is the last signed APK on file and predates the current source, so source-level findings should not be assumed to describe that APK without matching build provenance. No product code was changed and no tests were run for this report.
