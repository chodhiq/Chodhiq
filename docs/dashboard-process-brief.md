# ChodhiQ Web Dashboards — Senior Auditor Process Brief

**Prepared:** 5 November 2026  
**Scope:** provider business dashboard, web admin dashboard, their Supabase workflows, permission boundaries, and impact of `20261106100000_protect_verification_and_provider_fields.sql`.

## Executive summary

ChodhiQ has two web dashboards sharing the same Supabase project and public browser credential. The provider dashboard is an authenticated owner workspace; the admin dashboard is a privileged operations console. Both use a browser Supabase client with `NEXT_PUBLIC_SUPABASE_ANON_KEY` and rely on the signed-in user's JWT plus RLS. The admin UI also uses trusted Edge Functions for Auth administration. The browser does not contain or use a service-role key.

The provider dashboard has meaningful transactional RPC use for application submission, imported listing claims, verification submission, hours replacement, quote responses, and checkout initiation through an Edge Function. Several ordinary owner operations still write directly through PostgREST. The new provider trigger blocks a legitimate profile save because its direct update includes protected `updated_at`; this is the clearest newly introduced provider workflow failure. Verification request INSERTs are forced to `pending`, even when the UI asks to create a `draft`, which likely disrupts the staged evidence-upload workflow. Its pending-status fallback writes pass the verification trigger only where protected ownership fields remain unchanged, but do not establish a well-formed evidence-request lifecycle.

The admin dashboard workflows are inventoried in the companion [dashboard-workflows.md](dashboard-workflows.md). That earlier inventory requires status/count reconciliation before it is used as an authoritative finding: during this audit I confirmed `review_business_application` is defined in the shared business-application migration. Other reported missing RPCs need target-environment verification because the dashboard README identifies a local staging SQL surface. Highest risks for this brief are direct writes of provider trust fields, verification draft insertion semantics, and advertising page references to an absent shared performance relation.

This is a source/migration audit, not a live production control test. Any out-of-band SQL/function deployment may change runtime results. No environment-file contents or secret values were inspected.

## 2. Provider dashboard process

### Entry, authentication, and gate

The primary application route is `/` (`business-dashboard/app/page.tsx`). Public legal routes are `/terms`, `/privacy`, `/retention-policy`, `/moderation-policy`, `/delete-account`; auth confirmation is `/auth/confirm`. A provider signs in with email and password; the UI also supports account creation, confirmation resend, password reset, and sign-out (`business-dashboard/app/page.tsx:513-806`; account confirmation route `business-dashboard/app/auth/confirm/page.tsx`). `useBusinessDashboard` restores and listens to the Supabase session (`business-dashboard/lib/use-business-dashboard.ts:22-174`). The application gates in sequence: setup configuration → recovery → sign-in → business application when no owned provider exists → verification evidence screen until verified → owner workspace (`business-dashboard/app/page.tsx:284-334`).

Owner dashboard sections are Overview, Bookings, Calendar, Services, Team, Customers, Reviews, Earnings, Settings, Promotions, Leads, Analytics, Plans. Several labels share component behavior: Team/Settings use Profile plus Verification; Calendar uses Hours; Customers uses Reviews; Earnings uses Analytics (`business-dashboard/lib/business-dashboard-domain.ts:107-124`; `business-dashboard/app/page.tsx:452-506`).

## 3. Admin dashboard process

The full per-action admin inventory, including exact source file:line references, writes, permissions, UI errors, guard status, and likely breakages is in [dashboard-workflows.md](dashboard-workflows.md). This section summarizes the operational model and critical admin paths for auditor orientation.

### Login and routes

Admin sign-in uses Supabase Auth password login (`admin-dashboard/app/components/admin-shell.tsx:682`). `AdminGate` requires `session.user.app_metadata.role === 'admin'`; otherwise it shows “Administrator role required” and sign-out (`admin-dashboard/app/components/admin-shell.tsx:378-413`). Permissions in the nav are derived from `app_metadata.admin_level` and the local matrix (`admin-dashboard/lib/permissions.ts`). Database `is_admin()` and `admin_has_permission()` and restrictive RLS policies are authoritative (`supabase/migrations/20261023110000_admin_permission_enforcement.sql`).

Routes: `/`, `/applications`, `/providers`, `/providers/[id]`, `/verification`, `/activity`, `/demand`, `/users`, `/categories`, `/reviews`, `/community`, `/community/privileges`, `/moderation/community`, `/moderation/providers`, `/reports/community`, `/reports/providers`, `/campaigns`, `/notifications`, `/analytics`, `/payments`, `/subscriptions`, `/admins`, `/audit`. Monetisation routes are shown only with `NEXT_PUBLIC_ENABLE_MONETISATION`.

### Admin decision and operations paths

- **Business applications:** queue reads `business_applications`; decision calls `review_business_application`, which atomically changes application state, provisions provider on approval, and writes audit record. Shared production migration defines it in `20260909100000_business_applications.sql`; note discrepancy in the prior companion inventory: it was incorrectly described as local-only. UI sends applicant notification afterward; notification failure is non-transactional and visible separately.
- **Provider verification:** `admin_decide_verification` SECURITY DEFINER RPC requires `applications.review`; validates state, revision and evidence; changes verification request and (for approve/revoke) provider trust state; writes `admin_audit_log`. Notification on requested changes/revocation follows afterward.
- **Reports:** `admin_resolve_report` SECURITY DEFINER RPC transactionally updates report and may moderate target. `admin_transition_community_post`/`admin_transition_community_comment` similarly own moderation decisions. These definitions are present in dashboard-local staging SQL; verify the exact target production schema before treating them as operational. User sees generic `admin.act` mutation toast on RPC error.
- **Provider administration:** dossier edit and suspend/restore and bulk suspend are direct client `providers.update` operations. Dossier writes editable business fields plus `sponsored_rank`; suspend writes `verification_status,is_verified`; bulk suspend writes the same protected pair. They are subject to provider trigger and must be sent through trusted admin RPC path if authenticated database role is not `is_admin()`.
- **Other operations:** user suspend/reactivate and admin role grant/change/revoke use server Edge Functions with service role; categories/review moderation are direct RLS-gated writes; community privileges and notifications use RPCs; campaign management is direct table/storage writes; payments, activity, demand, analytics and audit are read-only/export workflows. Per-workflow table and column details remain in the companion inventory.

### Exact trigger behavior to consider

- Verification INSERT by ordinary `authenticated`/`anon` is not rejected: `status` is set to `pending`, and decision metadata is nulled. This silently conflicts with provider UI's draft-then-upload sequence.
- Verification UPDATE rejects changes to `status,reviewed_by,reviewed_at,admin_notes,decision_note,decision,decided_at,updated_by,provider_id,submitted_by`. The current provider dashboard's ordinary evidence upload does not update these columns, so it is not affected on UPDATE. RPC decisions bypass trigger and perform explicit authorization.
- Provider UPDATE protects identity/ownership, verification/reputation, timestamps, imported-source, promotion, status/publication/moderation/admin fields. In particular `updated_at` and `sponsored_rank` are included. Owner profile form sends `updated_at` itself; omitting it is the smallest owner-profile correction. Admin direct writes of protected provider fields can fail where the authenticated DB identity does not satisfy `is_admin()`.
- The trigger cannot distinguish authorized dashboard action type on `providers`; it returns early for any `public.is_admin()`. Therefore per-action permissions still must be enforced by RLS or RPC. A new trusted provider mutation RPC should explicitly check `admin_has_permission('providers.suspend')` for suspension and a deliberately chosen permission for edits.

## 5. Audit trail and operator-visible failures

Admin `admin.act` creates a correlation id, prevents duplicate concurrent action, checks session/admin JWT role, executes the mutation, then directly inserts `admin_audit_log`. For successful mutations, audit insert failure is reported as “The change succeeded, but its audit record failed. Stop and contact support before retrying.” Server-audited RPCs skip the follow-up insert because they write audit in their transaction. Generic database failures are shown as “The action could not be completed. Refresh and retry.” (`admin-dashboard/lib/admin.tsx:119-194`). Provider UI usually displays Supabase error text directly; booking and lead conflicts have explicit stale-state messages.

Admin audit completeness is therefore path-dependent: RPC workflows can atomically audit; client writes with `admin.act` mutate first and audit second (partial success possible); some providers-side operations have no explicit audit row in the browser handler and rely on DB-side audit triggers or downstream function logging. Verify those triggers and function logs in target environment.

## 6. Senior auditor verification priorities

1. **Confirm actual production object inventory** against shared migrations: `admin_resolve_report`, `admin_transition_community_post`, `admin_transition_community_comment`, `ad_campaign_performance`, campaign status columns/policies, and required storage bucket policies. Treat local staging SQL as non-production evidence until independently confirmed.
2. **Reproduce provider profile save with a verified owner after guard migration.** Expected current result: trigger rejects `updated_at`; remove client timestamp in the smallest fix, then verify database still maintains timestamps.
3. **Walk evidence request lifecycle.** Create verification through provider UI, upload evidence, observe status immediately after first insert, then invoke `submit_provider_verification`; the insert guard likely sets `pending` too soon. Check whether request is reviewable before documents arrive.
4. **Test identity classes:** authenticated owner, admin with `applications.review`, admin without it, anon, service-role Edge Function, and SECURITY DEFINER RPC caller. Verify trigger branch and effective role semantics.
5. **Test admin provider actions** for each admin level and confirm `providers.suspend` is checked by DB policy/RPC. Since provider trigger's bypass is `is_admin()` alone, do not infer least privilege from client nav hiding.
6. **Verify audit atomicity and alerting:** force an audit insert failure after a direct mutation; verify operator sees partial success; confirm RPC audits include actor, reason, before/after state and correlation id.
7. **Exercise owner data isolation** with two provider accounts for profile, services, hours, reviews/replies, bookings, leads, analytics, promotion media, notifications, and application/proof storage.
8. **Validate launch flags and payment controls:** `NEXT_PUBLIC_ENABLE_PAYMENTS` plus server `ENABLE_PAYMENTS`; exercise both disabled and enabled test flows without exposing secret material.
9. **Check lifecycle and recovery:** email confirmation, password reset, business application resubmission, rejected/changes-requested reapply, claim conflicts, booking/lead concurrent transitions, and account deletion retention cleanup.
